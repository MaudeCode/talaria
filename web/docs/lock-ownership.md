# Filesystem lock ownership

Process-wide locks may protect an atomic local-state transaction. The catalog,
runtime reload/publication, Talaria pairing, Gateway lifecycle, repository Git,
application-update, and Windows session-index replace coordination exceptions below
include bounded waits, subprocesses, sleeps, or network work because exposing
their partially mutated shared state would be unsafe. The environment resolver named
below is the callback exception; other listed locks do not cover network, model, tool,
subprocess, callback, queue-wait, join, or sleep work.

| State owner | Lock and contention domain | I/O kept inside and why |
|---|---|---|
| Agent configuration | `api.config._cfg_lock`; configuration readers, reloaders, and writers for all HTTP threads | Cold or stale snapshot reads hold the lock across `config.yaml` stat, complete read/YAML parse, cache publication, and snapshot copy; `_yaml_file_cache_lock` is released during parsing, but the outer lock keeps readers from observing a partial refresh. Writers hold it across one read-modify-atomic-write transaction so concurrent updates cannot be lost. |
| Profile configuration cache | `api.routes._PROFILE_CONFIG_CACHE_LOCK`; cached profile-config readers across all profiles | A metadata-identical cache hit opens, reads, and compares the complete profile `config.yaml` while holding the process-wide cache lock. The content check detects in-place rewrites that preserve inode, mtime, and size; cache misses parse outside the lock. A slow profile filesystem can therefore delay concurrent cached profile lookups. |
| Runtime reload commands | `api.commands._CODEX_RUNTIME_LOCK`, `_RELOAD_MCP_LOCK`, and `_RELOAD_SKILLS_LOCK`; one command family per process | Codex-runtime switching holds its lock across config read/mutate/atomic-write/reload. MCP reload holds its lock across shutdown and network-backed rediscovery. Skills reload holds its lock across the complete disk rescan. Each command-level single-flight prevents overlapping requests from interleaving teardown/rebuild or publishing a partially reloaded runtime; unrelated command families remain independent. |
| Agent runtime publication | `api.agent_runtime._RUNTIME_LOCK`; all lazy Agent-class readers | One process-wide single-flight verifies the loaded Agent revision, imports/publishes `AIAgent` on a cold or retried lookup, and captures the source revision. For a tracked checkout, revision verification may run three Git subprocesses with a two-second timeout each. Serialization prevents concurrent readers from publishing a mixed or partially initialized runtime. |
| Models catalog | `api.config._available_models_cache_lock`; all cold `/api/models` readers | One single-flight catalog build and cache publication. The normal path delegates live probes to a daemon worker and waits at most the configured four-second budget while holding the reentrant coordination lock; publishing includes the atomic disk-cache write. The operator-only `budget <= 0` compatibility mode performs the live rebuild synchronously under the same lock and is intentionally unbounded. This scope prevents duplicate provider probes and conflicting cache publishers. |
| Session index | `api.models._INDEX_WRITE_LOCK`; session metadata writers. `Session.save()` reaches it through the `_INDEX_FLUSH_COND` coalescing gate. The prune path additionally nests process-wide `api.config.LOCK` while reading | `_index.json` read/repair/atomic-write must observe one ordered session mutation. `_INDEX_FLUSH_COND` guards only the pending-row publish, batch handover, and outcome publication, never file I/O: a save arriving while another thread is rewriting the index publishes an immutable snapshot of its row into the pending batch and waits until the rewrite carrying that batch finishes, then reports its outcome, so every saver still observes its own index write as it did before coalescing. A saver performs at most one rewrite — its own batch — and then publishes that batch's result and drops the flusher role in one critical section, waking whichever saver is still waiting to perform the next one; it never stays on to drain later arrivals, so one session's mutation lock cannot be pinned behind unrelated sessions' saves. A rewrite that raises is recorded on its batch and re-raised by every saver in it, and the role still passes on, so a failure strands nobody. Cache population from unserialized index reads is signature-guarded outside this lock, so a mid-read replacement is never published as a write baseline. `prune_session_from_index()` holds the session-cache lock across the complete index read/JSON parse and pruned-payload snapshot, so slow storage there also delays unrelated `SESSIONS` cache users; the atomic write occurs after releasing that nested lock. On Windows, atomic replacement may sleep for 50/100/200/400 ms while retrying a cross-process `PermissionError`, adding at most roughly 750 ms to the index-lock scope. Transcript resolution and Agent database reads are outside these locks. |
| Session mutations | Per-session lock from `api.config._get_session_agent_lock`; one conversation's holders and waiters | In-memory mutation and `Session.save()` are serialized with the full session-sidecar atomic write and the nested index refresh, which a concurrent save's flusher may perform on the saver's behalf while it waits. Targeted workspace-binding recovery similarly holds the lock across sidecar read, fsync, atomic replacement, cache update, and index refresh. The weak `SESSION_AGENT_LOCKS` registry preserves one lock for overlapping work without retaining deleted session IDs; unrelated sessions remain independent. |
| Compression recovery start | `api.routes._COMPRESSION_RECOVERY_START_LOCK`; focused-continuation starts across all sessions and profiles | One process-wide transaction enumerates persisted session IDs, reads candidate sidecar metadata, creates and saves the focused continuation when absent, and publishes it to the session cache/index. Global serialization preserves the no-duplicate-child invariant for repeated recovery requests, including requests resolved through different source-session objects. |
| CLI session cleanup | Per-profile lock from `api.models._cleanup_manifest_thread_lock`, nested with that profile's persistent `.session_cleanup.lock`; delete requests in one process and across WebUI processes | One delete transaction includes stale-manifest recovery, SQLite row deletion, cleanup-manifest atomic publication before commit, and post-commit artifact scans, deletions, and manifest rewrites. The in-process and cross-process locks prevent concurrent cleanup from losing retry state or deleting artifacts for a still-live session; unrelated profiles remain independent. |
| Zero-message orphan tombstones | `api.models._WEBUI_ZERO_MESSAGE_ORPHAN_TOMBSTONE_LOCK`; sidebar prune and session-save writers | One bounded tombstone load, record/clear mutation, and fsync/atomic-replace or final unlink. The transaction prevents concurrent pruning and revival from losing each other's decision. |
| Deleted-session tombstones | `api.models._WEBUI_DELETED_SESSION_TOMBSTONE_LOCK`; delete and session-recreation writers | One bounded tombstone load, record/clear mutation, and fsync/atomic-replace or final unlink. Keeping the whole transaction ordered prevents a concurrent save/import from resurrecting an explicitly deleted WebUI session. |
| Composer drafts | Per-session lock from `api.session_drafts._draft_lock`; one conversation's draft readers/writers | One bounded draft-sidecar read or version-check/write/fsync/atomic-replace/delete transaction. Unrelated sessions use different weakly held locks; serialization prevents stale autosaves from overwriting a newer revision or reviving a deleted draft. |
| Auth sessions | `api.auth._SESSIONS_LOCK`; in-memory cookie lookup/mutation only | No file I/O remains under this lock. `_SESSIONS_PERSIST_LOCK` serializes an atomic write from a fresh snapshot after releasing state ownership, so slow storage cannot block authentication reads. Every validly shaped logout enters that persistence lane even when another logout already removed the token in memory, joining the outstanding write before reporting idempotent invalidation complete. |
| Password hash | `api.auth._AUTH_HASH_LOCK`; cold/invalidated password verification setup for all auth requests | One single-flight settings read/JSON parse and, for an environment-supplied password, one 600,000-round PBKDF2 derivation populate the process cache. Warm auth requests read the cached hash without the lock; invalidation deliberately makes the next request pay this bounded setup once. |
| Login attempts | `api.auth._LOGIN_ATTEMPTS_LOCK`; login rate-limit decisions for all request threads | One `.login_attempts.json` prune/append/clear read-modify-atomic-write keeps the persisted limiter consistent with the decision just returned. The file contains at most the bounded active-window attempts per client; password hashing and external identity work are outside this lock. |
| Passkey challenges | `api.passkeys._CHALLENGES_LOCK`; challenge writers/consumers | One bounded challenge-file load, expiry prune, mutation, and atomic write. The lock makes each challenge single-use and prevents concurrent stores from losing entries; cryptographic verification runs after release. |
| Public share snapshots | `api.shares._SHARE_LOCK`; share create/revoke mutations | One token file read-modify-atomic-write. The snapshot is already sanitized and bounded before lock acquisition; readers do not take the mutation lock. |
| Extension state | `api.extensions._EXTENSION_STATE_LOCK`; all administrator extension mutations | Manifest/state read-modify-atomic-write; consent grant may mint its sidecar token before commit. Gallery installation extracts its already-downloaded and verified archive under this lock, and uninstall scans/deletes the recorded file set before updating the manifest. Archives are capped at 1,024 files and 320 MiB uncompressed; serializing the complete transaction prevents partial install/uninstall state from becoming visible. Registry download and archive validation run before acquisition. |
| Extension sidecar tokens | `api.extension_sidecar_auth._LOCK`; token mint/reset for all extensions | One bounded stable read or create/reset transaction, including temp write, fsync, atomic link, permission hardening, and final reread. The lock prevents duplicate in-process minting; ordinary cached reads perform stable file I/O outside it. |
| Media snapshots | `api.media_snapshots._LOCK`; snapshot capture writers | One bounded source open/hash/copy, digest binding update, and quota scan/eviction. Serialization preserves the authorized file-handle-to-digest binding and prevents concurrent quota writers from losing sidecar state; snapshot reads do not take this lock. |
| Provider cost snapshots | `api.providers._COST_SNAPSHOT_LOCK`; daily cost-history writers | One provider snapshot read-modify-atomic-write, nested with its per-provider filesystem lock for cross-process ordering. Network usage fetches and delta calculation run outside the lock. |
| Provider quota scope identity | `api.providers._quota_scope_id_lock`; first identity reader for the server process | One `.quota_scope_id` read or first-create temp write/atomic replace, then a permanent in-memory cache hit. Serialization ensures concurrent first readers publish and use one stable opaque namespace. |
| Profile skill statistics | Per-profile lock from `api.profiles._SKILLS_STATS_LOCKS`; one profile's concurrent status readers | On a cache miss, one bounded skill-tree mtime walk plus `SKILL.md` discovery/frontmatter parsing populates the five-minute cache. Different profiles use different locks; serializing a cold miss prevents a thundering herd from multiplying the same overlay/filesystem scan. |
| Profile list | `api.profiles._LIST_PROFILES_CACHE_LOCK`; all concurrent profile-list readers | A cold or expired cache build enumerates every profile and reads its bounded configuration/metadata, gateway status, and cached/per-profile skill statistics before publishing the ten-second list snapshot. The outer single-flight lock prevents duplicate all-profile scans; warm reads return the cached rows. |
| Profile environment files and runtime credential resolution | `api.streaming._ENV_LOCK`; `.env` writers and Anthropic runtime-provider resolvers across profiles | One `.env` load, key mutation, temp write, fsync, permission restore, and atomic replace in `api.providers._write_env_file`. The shared lock preserves the read-modify-write transaction and pairs it with the bounded live-process env update. `api.oauth.resolve_runtime_provider_with_anthropic_env_lock()` also invokes its supplied resolver callback while holding this lock so credential reads cannot observe half-cleared Anthropic environment state; resolver work can therefore delay writers and other credential resolutions. Agent turns no longer hold the lock for their full duration. |
| Process-wide profile switch | `api.profiles._profile_lock`; process-wide profile switchers | One active-profile transition clears the skills cache, changes `HERMES_HOME` and module path globals, reads/parses the selected profile's complete `.env`, and replaces the previously loaded environment keys. The lock keeps those process globals aligned; the sticky `active_profile` write and configuration reload run after release. Per-client profile switches do not enter this process-wide mutation path. |
| Agent cron import path | `api.routes._AGENT_CRON_IMPORT_PATH_LOCK`; all lazy cron-package path initializers | One process-wide initialization scans and mutates `sys.path`, resolving entries and checking for competing `cron/__init__.py` files, then evicts an on-disk shadow package before publishing the ready path. Serialization prevents concurrent imports from observing a partially reordered module path. |
| Cron creation snapshot | `api.routes._CRON_CREATE_SNAPSHOT_LOCK`; selected-profile cron-create requests missing a provider or model snapshot | One snapshot resolution reads/parses the selected profile's `config.yaml` and `.env`, installs the background-worker profile context, and computes the provider/model pair before publication. Serialization keeps the pair bound to one profile-owned environment snapshot instead of mixing concurrent selections. |
| Cron profile operations | Nested `api.profiles._PROFILE_ENV_SCOPE_LOCK` and `_cron_env_lock`; all profile-scoped cron routes | One cron handler runs while the selected profile's process environment and cached cron module paths are installed, so its `jobs.json` reads/writes and manual-run setup cannot observe another profile's globals. The scope is all-profile and lasts for the handler; Agent turns and unrelated non-cron routes do not enter it. |
| Run journals | Per-journal path lock from `api.run_journal._WRITER_LOCKS` | Append/flush ordering for one `(session, stream, path)`. Retention uses the same path lock across stat/tail reads, pruned-summary atomic write, and journal unlink so pruning cannot remove a file while a writer appends. Unrelated journals use different locks; global guards protect lock/cache dictionaries without file I/O. |
| Lazy run-journal recovery | Per-session nonblocking lock from `api.models._journal_retry_lock_for_sid`; one session's read-side recovery callers | One recovery attempt performs durable journal reads and arrival checks, mutates recovered messages or retry metadata, and persists the session before releasing the lock. Nonblocking acquisition prevents duplicate recovery and writes for the same session; unrelated sessions remain independent and the weak retry-lock registry is cleaned after each attempt. |
| Project metadata | `api.models._PROJECTS_MUTATION_LOCK`; project/cron/webhook metadata writers and the aliased `_PROJECTS_MIGRATION_LOCK` | Normal `projects.json` lookup-or-create/read-modify-write transactions prevent parallel profile projections from overwriting each other. On the first legacy migration, the same process-wide lock additionally covers a complete session-index read/JSON parse, profile backfill, and migrated project write; a waiter may reread `projects.json` after another thread completes. Normal session scanning and external work remain outside the lock. |
| In-place compatibility writes | `api.paths._IN_PLACE_WRITE_LOCK`; rare config/profile targets that cannot use atomic rename | One verified-inode truncate/write/mode-restore/fsync sequence. Normal writes use same-directory temp files and atomic replace without this global lock; the compatibility lock exists only to prevent byte interleaving when inode preservation is mandatory. |
| Workspace Git mutations | Per-repository lock from `api.workspace_git._git_mutation_lock`; one canonical repository | Subprocess-backed checkout, stage, commit, fetch, pull, and push sequences hold the repository lock across their complete index/worktree/ref transaction. Different repositories use different locks; readers use hardened read-only commands without the mutation lock. |
| Workspace Git status cache | `api.workspace_git._STATUS_CACHE_GUARD`; the polled status routes plus every `git_status` scan and mutation helper | Guards only the in-memory status payload and the per-repository generation counters, never a subprocess. Reuse is opt-in (`git_status(..., use_cache=True)`) and limited to `/api/git/status` and `/api/git-info`; callers that decide from the payload always read fresh. A reader revalidates the stored `.git/index` and `HEAD` stat fingerprint under the lock, and a scan republishes only if the generation it captured before its reads is unchanged. `_git_mutation_lock` bumps that generation and drops the repository's entries as it releases, so a stage, commit, or untracked-file discard cannot be answered from a pre-mutation payload. Working-tree edits leave `.git` untouched and bound the polled path by `STATUS_CACHE_TTL` alone. |
| Background-process recovery | `api.background_process._PROCESS_RECOVERY_LOCK`; all WebUI startup recovery callers | One process-wide single-flight covers checkpoint recovery, recovered-process enumeration, process lookup, and metadata-only owner-session resolution, which may read and parse cold session sidecars. It prevents duplicate recovery and publishes the recovered-once flags only after the registry-to-WebUI routing scan finishes. |
| Talaria pairing and publisher transition | `api.talaria_relay._pairing_lock`; all pairing requests, nesting `_publisher_transition_lock` during publisher validation/swap | One complete registration or profile-enrollment transaction reads/creates profile identity, loads relay state, performs the ten-second network request, atomically writes the private key and configuration, then validates and publishes the initial snapshot before swapping publishers. The pairing lock prevents duplicate invitation redemption or conflicting credentials; the transition lock keeps publisher listener, terminal-state, revision, and live-instance handoff atomic. |
| Gateway lifecycle action | `api.routes._GATEWAY_ACTION_LOCK`; all authenticated start/stop/restart requests | Nonblocking single-flight acquisition covers Agent-checkout resolution and entrypoint existence checks plus the complete `hermes gateway` subprocess, bounded by 60 seconds. It prevents overlapping lifecycle commands from racing the same service state; a concurrent request receives 409. |
| Gateway background restart | `api.gateway_restart._GATEWAY_RESTART_LOCK`; all active-profile restart helpers | Nonblocking single-flight acquisition covers profile/command discovery, process launch, the quick completion window, and, when draining continues, the background process wait bounded at 240 seconds plus bounded terminate/kill reap attempts. The lock is released only after the one restart process completes or is terminated. |
| Application update | `api.updates._apply_lock`; all WebUI self-update attempts | One fetch/status/stash/pull-or-fast-forward/stash-pop sequence, including Git network and subprocess work. The process-wide single-flight prevents concurrent update attempts from observing or publishing a half-applied checkout; status/cache reads remain independently available. |

When a local filesystem operation fails, its owning API returns or logs an
explicit degraded/error result and never silently uses another profile's state.
Auth session persistence is the documented availability exception: failure to
replace `.sessions.json` is logged, while the newly signed session remains valid
in the process-local session map until restart. Callers therefore receive a
working cookie, but that login is explicitly best-effort durable rather than a
committed disk mutation. Extension uninstall is also best-effort at the asset
layer: per-file/directory removal errors are ignored and the manifest entry is
still removed, so a successful response can leave untracked extension files on
disk; reinstall/administrator cleanup is the recovery path.
